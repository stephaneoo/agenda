# Local events agenda, v1: from DATAtourisme to occurrence pages

## Intent

An agenda of events within driving reach of Nyons, for both the people who live there and the people passing through. A visitor picks a town and a radius in **car travel time**, and gets the matching events in a dense, no-nonsense list. Opening the site shows the agenda itself, with no landing page and no marketing copy. The hard part is feeding events, not displaying them. v1 is the first vertical slice: DATAtourisme ingestion, the claims model, the filtered list, one page per occurrence with Google-compliant JSON-LD, a public read API, offline reading, and operations a non-technical colleague can run with Claude.

v1 succeeds when:
- every DATAtourisme event in the covered area appears within about a day of the office publishing it;
- every occurrence page passes Google's Rich Results Test as an event;
- a visitor who loaded the site once can still browse and filter it with no network;
- the colleague deploys with one command, and a broken deploy rolls itself back.

## Goals, non-goals, anti-goals

* Goal: nightly ingestion of DATAtourisme events for the covered area, stored as per-source claims.
* Goal: a list page filtered by town, travel time, date range and category, server-rendered, with a small JS island.
* Goal: one page per occurrence, with schema.org `Event` JSON-LD that conforms to Google's event structured data.
* Goal: a versioned public read API, documented by OpenAPI. The web UI uses only this API and server-side code. It has no private endpoints.
* Goal: offline reading. The agenda, the occurrence pages already visited, and the town/radius filter all work without a network.
* Goal: post-moderation in the Django admin. Hide or restore an event or a single occurrence, with a reason. Edit fields. All of it survives the sync.
* Goal: NixOS host with Caddy, PostgreSQL + PostGIS on ZFS, offsite backups with a tested restore, one-command deploy with automatic rollback.
* Non-goal (v1): direct submission form, MCP server (read and write tools), organiser accounts, trust levels, rate limits. *(Claude's call: MCP waits for v2. It plugs into the same service layer, so nothing in v1 blocks it.)*
* Non-goal (v1): ICS, RSS, ActivityPub and Bluesky feeds; write-back to Apidae; the Meta mention pipeline; Haiku-assisted moderation.
* Non-goal (v1): images. DATAtourisme's simplified export has none, and images carry their own rights.
* Non-goal (v1): any UI language other than French. Offline drafting by organisers.
* Anti-goal: stale data that looks current. The agenda must always show when it was last synced, and when the offline copy was saved.
* Anti-goal: a hidden event coming back after a sync, or a moderator's edit being overwritten.
* Anti-goal: a partial or failed import wiping out events. A failed fetch must never be read as "these events were deleted".
* Anti-goal: blabla. Any page or block whose content isn't events, filters or required attribution.
* Anti-goal: scraping closed platforms, or any automation that evades detection.

## Constraints

* Single VM. Scaleway *(Claude's call, matching the leaning in context.md)*. Source: user.
* NixOS, with every service as a Nix module or package, and no docker. Source: [0001](../decisions/0001-nixos-with-pure-nix-packaging.md).
* ZFS for data, unencrypted. PostgreSQL with PostGIS. Source: user.
* Caddy as the web server. Source: user.
* Django monolith: Django admin, django-ninja for the API, management commands on systemd timers. Source: [0002](../decisions/0002-django-monolith.md).
* Zero-downtime migrations. Every breaking schema change is split over two deploys (expand, then contract), enforced by a check. Source: user, [0002](../decisions/0002-django-monolith.md).
* Deploys go from the colleague's laptop, with git and one command. All checks run first, and the deploy is refused if any fails. No CI. Source: user, [0001](../decisions/0001-nixos-with-pure-nix-packaging.md).
* The event is the primary record. Each occurrence has a stable URL. Source: [0004](../decisions/0004-event-first-model.md).
* Per-source claims. Reads only touch the precomputed canonical tables, which only the projection code writes. Source: [0005](../decisions/0005-claims-with-precomputed-projection.md).
* AGPL code, Licence Ouverte data, reserved branding. DATAtourisme attribution includes the source and its last update date. Source: [0003](../decisions/0003-licences.md).
* Backups go offsite, to another region, and are tested by restoring them. Source: user.
* Imported events are post-moderated: they are published automatically. Source: user.

## Approaches

The app-server options were Django, PostgREST plus a second service, and Rust. Pierre picked Django to keep it simple ([0002](../decisions/0002-django-monolith.md)). Rust was dropped for lacking an automatic admin. For the data, Pierre picked event-first, like DATAtourisme ([0004](../decisions/0004-event-first-model.md)), over occurrence-first. For storage, he picked per-source claims with a precomputed projection ([0005](../decisions/0005-claims-with-precomputed-projection.md)), over a merged record with or without raw copies. NixOS with native modules won over Debian with compose ([0001](../decisions/0001-nixos-with-pure-nix-packaging.md)). Caddy won over Envoy and nginx.

## Specification

This section defines the public read API v1 and the JSON-LD on occurrence pages. Other clients (agents, the future MCP server, third parties) rely on both.

The key words MUST, MUST NOT, SHOULD, SHOULD NOT and MAY are to be interpreted as described in RFC 2119 and RFC 8174 when, and only when, they appear in all capitals.

### Terminology

* **Event**: an identifiable happening with one or more dates, such as "Marché de Nyons". It is the primary record.
* **Occurrence**: one dated instance of an event. It has its own ID and its own public page.
* **Commune**: a French commune, identified by its 5-character INSEE code (`26220`, or `2A004` for Corsica).
* **Covered area**: the set of communes the agenda collects events for. In v1, every commune whose reference point is within 30 minutes' drive of Nyons.
* **Travel time**: the car travel time in whole minutes between two communes' reference points, read from a precomputed matrix. It is measured commune to commune, not address to address.
* **Local date-time**: an RFC 3339 date-time with the UTC offset in force in `Europe/Paris` at that instant, such as `2026-11-07T21:00:00+01:00`.

### Structure

**General**
* The base path MUST be `/api/v1/`. Responses MUST be `application/json; charset=utf-8`, except for errors.
* The server MUST serve the OpenAPI 3.1 description at `/api/v1/openapi.json`.
* Errors MUST be `application/problem+json` (RFC 9457), with `status`, `title` and `detail`.
* Field names MUST be `snake_case` and in English. Text content is in French.
* Clients MUST ignore fields they don't know.
* Lists MUST be paginated with an opaque `next` cursor. `next` is `null` on the last page. `limit` defaults to 50, and the server MUST reject values above 200.

**Endpoints**
* `GET /api/v1/occurrences` MUST accept these parameters:
  * `commune`: INSEE code of the origin. Required whenever `within` is given. It MUST be a commune in the covered area, otherwise the response is 422.
  * `within`: an integer from 0 to 60 inclusive. It keeps occurrences whose commune is at most that many minutes from `commune`. With 0, only the origin commune itself is kept. Any value outside that range gives 422.
  * `from`, `to`: local dates (`YYYY-MM-DD`), inclusive. `from` defaults to today in `Europe/Paris`. `to` defaults to `from` + 30 days. A span over 92 days MUST give 422, and so must `to` before `from`.
  * `category`: zero or more category slugs, repeated (`?category=marche&category=concert`).
  * An occurrence matches a date range if any part of it falls between `from` 00:00 and `to` 24:00 local time.
  * Results MUST be sorted by `start`, then by `id`.
  * Only published occurrences of published events are returned, including occurrences whose `status` is `cancelled` or `postponed`. Hidden ones MUST NOT appear.
* `GET /api/v1/occurrences/{id}` MUST return a single occurrence, including past ones. It MUST return 404 for an unknown ID. It MUST return 410 for one that is hidden or withdrawn, i.e. a future date that no source lists any more. For an occurrence a moderator moved to another date, it MUST return 301, with `Location` pointing to the new occurrence's API URL.
* Past occurrences are never withdrawn. They stay retrievable by ID, and `GET /api/v1/occurrences` only returns them when the requested date range includes them.
* `GET /api/v1/events/{id}` MUST return the event, with its published occurrences from today onwards in `occurrences`.
* `GET /api/v1/communes` MUST return the covered communes: `insee`, `name`, `lat`, `lon`.
* `GET /api/v1/travel-times` MUST return the matrix for the covered area as `{ "version": string, "communes": [insee…], "minutes": [[int|null…]…] }`. `minutes[i][j]` is the travel time from `communes[i]` to `communes[j]`, and `null` means unreachable.
* `GET /api/v1/categories` MUST return `[{ "slug", "label" }]`.
* `GET /api/v1/status` MUST return `{ "last_sync": local date-time | null, "sources": [{ "name", "last_success": local date-time | null }] }`.

**Occurrence object**
* `id`: string, stable across re-imports. MUST be present.
* `url`: absolute URL of its public page. MUST be present.
* `event_id`: string. MUST be present.
* `name`: string. MUST be present and non-empty.
* `description`: string or `null`. Plain text.
* `start`: a local date-time, or a local date (`YYYY-MM-DD`) when no time is known. MUST be present.
* `end`: same format as `start`, or `null`. When present, it MUST NOT be before `start`. A `null` end means "no end to display".
* `timezone`: MUST be `"Europe/Paris"`.
* `status`: one of `scheduled`, `rescheduled`, `postponed`, `cancelled`. MUST be present. `postponed` with `start` still set means "postponed, no new date yet": `start` is the original date.
* `previous_start`: same format as `start`, or `null`. MUST be set when `status` is `rescheduled`.
* `category`: a category slug. MUST be present (`autre` if nothing else fits).
* `location`: an object with these fields, and MUST be present:
  * `name`: string or `null`;
  * `street`: string or `null`;
  * `postal_code`: string;
  * `commune`: INSEE code;
  * `commune_name`: string;
  * `lat`, `lon`: numbers or `null`.
* `organizer`: `{ "name", "url" | null }` or `null`.
* `offers`: `{ "is_free": bool | null, "price": string | null, "url": string | null }` or `null`.
* `sources`: an array of at least one `{ "name", "url" | null, "licence", "updated_at" }`. It MUST name every external source whose claims contributed to a published field. `updated_at` is that source's last update date for this record (for DATAtourisme, the record's `Date_de_mise_a_jour`). This is what satisfies Licence Ouverte attribution. Our own moderation is not an external source and MUST NOT appear. An event whose every published field comes from moderation alone still lists the source that created it.
* `updated_at`: the local date-time of the last projection change.

**Event object**
* It has the occurrence fields `id`, `name`, `description`, `category`, `location`, `organizer`, `offers`, `sources` and `updated_at`, plus `occurrences`, an array of occurrence objects.

**Occurrence page JSON-LD**
* Each occurrence page MUST contain exactly one `<script type="application/ld+json">` with exactly one schema.org `Event`.
* It MUST contain `name`, `startDate` and `location`. `location` MUST be a `Place` with `name` (falling back to `commune_name`) and an `address` `PostalAddress` with `addressLocality`, `postalCode` and `addressCountry: "FR"`.
* `startDate` and `endDate` MUST use the same formats as `start` and `end`.
* `eventStatus` MUST be set: `EventScheduled`, `EventRescheduled`, `EventPostponed` or `EventCancelled`.
* `previousStartDate` MUST be set when `status` is `rescheduled`.
* `eventAttendanceMode` MUST be `OfflineEventAttendanceMode`.
* It SHOULD contain `description`, `organizer` (`Organization`, with `name` and `url` when known), and `offers` (an `Offer` with `url`, plus `price: 0` and `priceCurrency: "EUR"` when the event is free). `isAccessibleForFree` SHOULD be set when `is_free` is known.
* It MUST NOT contain `image` in v1.
* The page MUST be server-rendered, with the JSON-LD in the initial HTML.

### Versioning

* The version is the path segment `/api/v1/`.
* Non-breaking changes: adding an endpoint, adding an optional parameter, adding a field, adding a value to `category`. These MAY ship within v1.
* Breaking changes: removing or renaming a field or parameter, changing a type or format, adding a `status` value, tightening validation. These MUST go to `/api/v2/`. *(Claude's call)* v1 MUST then keep being served for at least 90 days, side by side with v2.
* `info.version` in the OpenAPI description MUST be bumped on every change to the API.

## Implementation

**Code layout** *(Claude's call)*. One Django project, with these apps:
* `geo`: communes, covered area, travel-time matrix;
* `claims`: sources, raw source records, claims, the projection;
* `agenda`: canonical `Event` and `Occurrence` tables, the read service layer, categories;
* `ingest`: DATAtourisme sync;
* `api`: django-ninja v1;
* `web`: pages, templates, static files, the service worker.

Python is packaged with uv2nix. Tests use pytest-django.

**Claims and projection**
* `SourceRecord(source, external_id, payload jsonb, payload_hash, fetched_at, last_seen_sync)`. This is the raw copy of what the source sent.
* `Claim(target_type: event|occurrence, target_key, field, value jsonb, source, seen_at)`. One claim per target, field and source. A newer value replaces the older one; history is kept in `ClaimHistory` *(Claude's call)*.
* *(Claude's call)* Source priority, highest first: `moderation` (100), `rules` (60), `direct` (50, v2), `datatourisme` (10). For each field, the highest-priority claim wins, and the newest `seen_at` breaks a tie. A rule can be replaced by recomputing the projection, so it isn't a fork.
* The visibility of an event or occurrence is a claim on `visibility` (`published` | `pending` | `hidden`, plus `reason`). Imports get `published` by default. Moderation claims override. The `rules` source exists, so a hold rule can be added later without schema change; v1 ships with no rules.
* *(Claude's call)* A source's presence is also a claim: a sync writes `listed: true|false` on each future occurrence it covers. An occurrence is shown only if at least one source has `listed: true` and the winning `visibility` is `published`.
* "Hide" writes a `moderation` visibility claim. "Restore" **deletes** that claim, so it removes the override and does not pin the event. A restored event that its source has since withdrawn stays withdrawn.
* Every write of claims recomputes the canonical rows for the affected event and its occurrences, in the same transaction. `manage.py rebuild_projection` rebuilds everything, and a test asserts that the rebuild equals the incremental result.

**Occurrence identity** *(Claude's call)*
* An occurrence's key is `(event, local start date)`. Its public ID is derived from that key, and its URL is `/evenements/<event-slug>-<YYYY-MM-DD>/`.
* **From periods to occurrences.** A period with a recurrence (weekdays, "every Tuesday") gives one occurrence per matching date. A continuous range with no recurrence (an exhibition from October to December, a festival from Friday to Sunday) gives **one** occurrence spanning the range, with `start` on its first day and `end` on its last.
* When a source stops listing a **future** date, the occurrence becomes `withdrawn`: it is no longer listed, and its page returns 410. Past occurrences are never withdrawn. Their pages stay up and show that the event is over.
* A new date is a new occurrence.
* **Moving an occurrence.** In the admin, a moderator can move an occurrence to a new date. That date may or may not already exist as an occurrence; if not, the move creates it through a `moderation` date claim.
  * The new occurrence gets `status: rescheduled` and `previous_start`.
  * The old occurrence gets a `moved_to` moderation claim. That claim outranks the source still listing the old date, so the old occurrence isn't listed any more.
  * The old URL returns a 301 to the new one, both on the web and in the API.
* Moderators can also set the status of a single occurrence: `postponed` or `cancelled`. DATAtourisme's simplified export carries no status, so this is how those statuses get set.
* Two showings on the same day are one occurrence, with the earliest start. *Accepted limitation for v1.*

**DATAtourisme ingestion**
* `manage.py sync_datatourisme` runs nightly on a systemd timer at 06:00 Europe/Paris, after the upstream export at about 03:00 UTC.
* It fetches the events dataset through the data.gouv.fr tabular API or the CSV resource, and keeps rows whose location falls in a covered commune. That commune is found from the row's coordinates by point-in-polygon, falling back to postcode plus commune name. Rows are never selected by postcode alone.
* Each row becomes a `SourceRecord` and a set of claims. `Periodes_regroupees` is parsed into dates. An end time earlier than the start time on the same date moves the end to the next day.
* **Deletion safety** *(Claude's call)*.
  * Withdrawals are counted per **future** occurrence. An occurrence that has simply ended is never counted and never withdrawn.
  * Future occurrences are withdrawn only if the sync finished cleanly, i.e. every page was fetched.
  * If a sync would withdraw more than 20% of the area's future occurrences, it still applies new and updated records but **skips all withdrawals**. It then records the run as `partial` and alerts.
  * `last_success` in `/api/v1/status` advances for a clean or a partial run, and the about page shows a partial run as such.
* Category mapping: DATAtourisme event types are mapped to a fixed list in code *(Claude's call)*. The slugs are `concert`, `spectacle`, `cinema`, `exposition`, `marche`, `brocante`, `fete`, `sport-balade`, `atelier-conference`, `loto-jeux`, `autre`. This is one filter axis; an editorial second axis is v2.

**Covered area and travel times**
* Communes come from INSEE's code officiel géographique and IGN Admin Express polygons. The reference point is the chef-lieu (town hall), not the centroid, because a centroid can sit on a mountain *(Claude's call)*.
* `nix run .#travel-matrix` runs on the laptop. It runs OSRM with the car profile on Geofabrik OSM extracts covering Drôme and Vaucluse plus their borders. It computes the reference-point × reference-point durations and writes a committed data file (`data/travel-times.json`), which `manage.py load_geo` loads.
* The covered area is every commune within 30 min of Nyons in that matrix. It is stored as data, so growing it means changing a parameter and reloading.
* An event's travel time is the travel time to its commune.
* The matrix is refreshed by hand, rarely.

**Web**
* French UI, plain CSS with no framework *(Claude's call)*, mobile first.
* `/` is the agenda, a dense list grouped by day. Each row shows time, category, title and commune. Occurrences spanning more than one day appear once, in an "En cours" group above the days, and are not repeated under each day *(Claude's call)*.
  * Filters: commune (select among covered communes, default Nyons), radius (0 / 10 / 20 / 30 min, default 30), dates (today, this weekend, 7 days, 30 days; default 7 days), category.
  * Filters are query parameters, so the server renders the right list with no JS.
* `/evenements/<slug>-<date>/` is the occurrence page, with JSON-LD. It shows attribution: the source and its update date.
* `/a-propos/` covers licences, attribution, the editorial charter (text supplied by Pierre before launch) and the last sync date.
* The footer of every page shows the last sync date.

**Offline (readers only)**
* A service worker precaches the app shell, CSS, JS, `/api/v1/communes`, `/api/v1/travel-times` and `/api/v1/categories`.
* On each online visit, it downloads the covered area's published occurrences for the next 30 days into IndexedDB. The whole covered area is small.
* With JS available, the filter runs client-side against that copy whether online or offline, so filtering is instant and works offline. Offline, a banner says "Données du <date>".
* Occurrence pages that were visited are cached, and others render from IndexedDB using a client-side template.

**Admin**
* Django admin over the canonical tables, read-only. Edits and the "hide" / "restore" actions (which require a reason) write `moderation` claims.
* Each event's admin page shows its claims per field, with source and date.
* Access is Django auth, for staff only.

**Operations**
* A NixOS flake defines the host: PostgreSQL with PostGIS, its data on a ZFS dataset; Caddy, with automatic TLS, in front of gunicorn; systemd timers for the sync and backups.
* Backups:
  * **Two buckets** in Scaleway Object Storage, both in a different region from the VM *(Claude's call: VM in fr-par, buckets in nl-ams)*:
    * **`wals`** is the pgBackRest repository: the base backups plus the WAL archive. pgBackRest keeps both in one repository, so they share this bucket.
    * **`assets`** holds media files, through django-storages. It is empty in v1 because there are no images yet. It exists now so that v2 doesn't change the infrastructure. Object versioning is on, and versions are kept for 6 months.
  * **Retention** (Pierre):
    * point-in-time recovery to any moment in the last **7 days**;
    * a daily backup for **30 days**;
    * a weekly backup for **12 weeks**;
    * a monthly backup for **6 months**.
  * *(Claude's call)* pgBackRest's own expiry can't express that grandfather-father-son scheme. Backups are labelled `daily`, `weekly` or `monthly` with `--annotation`, and a small expiry script deletes sets past their tier's age with `pgbackrest expire --set`. WAL is kept only as far back as the oldest backup still inside the 7-day window.
  * Target RPO is 5 minutes, and RTO is 4 hours *(Claude's call)*.
  * Hourly ZFS snapshots, kept 48 hours, for local rollback.
* **Restore is scripted** (Pierre). `nix run .#restore -- [--target-time <RFC 3339> | --set <label>]` is run from the laptop, and Claude may run it with the colleague, without Pierre:
  1. Restore into a **new** ZFS dataset with a fresh PostgreSQL instance. The live dataset is never written to.
  2. Run the sanity checks: the migrations match the deployed code, the canonical tables are non-empty, and the latest claim is no newer than the target.
  3. Snapshot the current dataset.
  4. Stop the app, swap the datasets, start the app, check `/healthz`.
  5. If anything fails, swap back. The previous dataset is kept for 7 days, and destroying it waits for Pierre.
* A monthly systemd timer runs steps 1–2 of the same script against the latest backup, and alerts on failure. That way the restore path used in an emergency is the one tested every month.
* **Status reporting** (Pierre): no external alerting service.
  * Each timer job (sync, backup, tier expiry, restore test) records its outcome (`ok` | `partial` | `failed`, timestamp, one-line summary) in `/var/lib/agenda/status.json`.
  * The server's MOTD renders that file. A job that hasn't succeeded within its expected interval (sync 26 h, backup 26 h, restore test 32 days) shows as **STALE**.
  * `nix run .#status`, run from the laptop, prints the same report over SSH.
  * `CLAUDE.md` tells every Claude session in this repo to start by asking Pierre whether he wants the server status (sync, backups, restore test, disk), and to run `nix run .#status` if he does.
  * "Alerts" elsewhere in this spec means: record `failed` or `partial` in the status file.
* `/healthz` returns 200 only when the database answers and migrations are up to date.
* *(Claude's call)* The laptop may be a Mac, so the checks and the system build run in different places, and nothing needs a local Linux VM:
  * The checks run natively on the laptop's own platform: pytest against an ephemeral PostGIS from Nix, the migration check, the OpenAPI diff, and the JSON Schema fixtures.
  * The NixOS system (x86_64-linux) is built on the production VM, with the VM as remote build host.
  * There is no NixOS VM test. Boot-level safety comes from deploy-rs magic rollback plus the `/healthz` check.
* Deploy is `nix run .#deploy`, run from the laptop:
  1. Refuse if the git tree is dirty, or if local `main` differs from `origin/main` after fetching branches and tags.
  2. Run the checks.
  3. Build on the VM, then deploy with deploy-rs, whose magic rollback reverts if the host doesn't confirm.
  4. Check `/healthz`, and roll back if it fails.
  5. Tag the commit `deploy-<UTC timestamp>` and push the tag to `origin`. The tags are shared, so the migration check has the same baseline whoever deploys.
* Migration check: lint the migrations added since the last `deploy-*` tag with django-migration-linter. A backward-incompatible operation fails the check, unless it is annotated as the contract step of an expand migration already present at the last deploy tag.
* `docs/ops/RUNBOOK.md` is written for Claude operating with the colleague. It lists the safe actions (deploy, rollback, re-run the sync, read logs, run the restore script) and the actions that wait for Pierre: changing backup configuration or retention, deleting backups or datasets, manual SQL, or other changes to the ZFS pool.
